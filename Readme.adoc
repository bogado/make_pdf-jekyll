= Make pdf Jekyll plugin.
Victor Bogado da Silva Lins <victor@bogado.net>
:toc: true

This is a https://jekyllrb.com/[Jekyll] plugin to enable the creation of PDFs along side the usual html documents.

== Installation

Add to your site `Gemfile` : 

[ruby]
----
# …
group :jekyll_plugins do
    gem 'make_pdf-jekyll'
    # … Other plugins may be here.
end
----

Then edit your Jekyll configuration. 

WARNING: The schema here is still in experimental phase.
Expect changes until version 1.0 reached.

[yaml]
. `_config`
----
# …
destination: «some-path» (1)
# …
plugins:
    - make_pdf/jekyll
    # … Other plugins.

make-pdf:
    writer: Chrome                              # Requires `Chrome-headless-render-pdf` to be installed and on the path.

    # Bellow are the default settings :
    write-by-default: false                     # If set to true enables the generation
    input-base-url: «some-relative-path»        # base path common to all input files.
    output-base-path: «some-path»               # base path where the pdf are stored.
    input-scheme: «http|file»                   # How to access the input HTML.
    input-host: «hostname»                      # Required when `input-scheme` is not `file`.
    output-dir: «some-path»                     # Path where to store pdf files.

    # Chrome-headless-render-pdf options : 
    no-margins: true                            # Do not use margins.
    include-background: true                    # Use backgrounds
    landscape: false                            # Don't use landscape.
    display-header-footer: false                # No header or footer.
    # There are more options for chrome.
----
<1> This is a limitation, I will update this in the future.

To each document that you want PDFs to be generated add the key `make-pdf: true` to it's front-matter.
If the option `write-by-default` is set to true, you can disable the PDF generation with `make-pdf: false` as well.

== How the PDF is created.

The option 'writer' defines the strategy used to generate the PDFs.
The only working option at the moment is 'Chrome', that uses 'Chrome-headless-render-pdf' to create the PDF.
This may not work correctly, depending on how the asset files are specified in the output 'html' files.

You can also use your 'published' version, by setting both `input-scheme:` and `input-host:` configurations.
Use `input-scheme: http` (or `https`) and `input-host: «hostname»` to point the headless chrome to the correct URL.

== Using front-matter

You can use the `front-matter` properties on your pages to setup any of the options set on the `_config` file.
Any option that starts with `make-pdf-` is read as targeted for this plugin.
Options defined on pages will take precedence over globally defined ones.

For example, setting `make-pdf-include-background: false` on you front-matter will stop `chrome` from printing the backgrounds for this document.

.Other configuration options
`make-pdf:`:: Enable or disable pdf generation for this page.
`make-pdf-name:`:: Use a different file name for the PDF of this page.
Useful for "index" pages, for example.

== Missing capabilities

1. Create PDF on both the "Target" and "Source" tree.
This will simplify the configuration by removing the choice of genarate on either of those places.
This will remove the need of adding the source of the PDfs to the `keep_files` configuration.

2. Take into account the different assets required to build the page when checking the need of updating the PDF.
This is a big task, requiring different levels of assets.

Css::: Required to capture change on layout
Images::: If an external image changes the PDF needs to be updated.
Asciidoc inclusions::: May change the actual document.
Scripts::: May change the layout.
+
--
[NOTE]
====
Scripts are out of the initial scope.

Pages with scripts are considered interactive.
That mean that either they are not suitable for PDFs.

The PDF generator will consider the cannonical form for PDFs as the page as rendered with scripts turned off.
====
--

== Known issues

WARNING: These are current limitations of the implementation, not intended behavior.

=== A missing PDF may never be regenerated

Regeneration is decided by hashing the source file and comparing it against a hash recorded on a previous run.
The plugin never checks whether the PDF still exists at `destination`.
If the PDF is removed from `destination` without the source content changing, for example by a clean rebuild on a CI pipeline where the hash cache persists but `destination` does not, the PDF will not be regenerated.
It will stay missing until the source page's content changes.

=== A failed generation crashes the build instead of being retried

The retry helper that wraps generation has a typo, it increments a variable that was never initialized.
Because of that, any failure from the writer (for example `Chrome-headless-render-pdf` crashing) raises a `NoMethodError` on the first attempt instead of retrying, aborting the whole Jekyll build.
Even once that is fixed, nothing currently stops a failed generation from being recorded as if it had succeeded, which would still leave it unretried on the next build.

=== `write-by-default` has no effect

Pages are only processed when they explicitly opt in with `make-pdf: true` on their front-matter.
Setting `write-by-default: true` on the `_config` currently does not change this.
